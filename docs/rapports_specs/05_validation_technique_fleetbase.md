# Rapport agent — Validation technique Fleetbase (fact-checking)

*Produit par un agent spécialisé Fleetbase, le 26 juillet 2026, chargé de vérifier chaque affirmation factuelle du journal d'exploration contre le code source public et la documentation officielle de Fleetbase. Reproduit ici intégralement pour traçabilité — la synthèse priorisée est dans `docs/specs_echango_delivery.md`.*

---

Méthodologie : chaque affirmation a été vérifiée directement sur le code source public (`fleetbase/core-api`, `fleetbase/fleetops-api`, `fleetbase/navigator-app`, `fleetbase/registry-bridge`, `fleetbase/fleetbase`, `fleetbase/customer-portal`, `fleetbase/ledger`) via `raw.githubusercontent.com` et les vues GitHub, complété par la documentation officielle (`fleetbase.io/docs`, `docs.fleetbase.io`) atteinte via recherche web quand l'accès direct était bloqué (403 persistant sur ce sandbox). Récupération faite via un outil de fetch qui repasse le contenu par un petit modèle — redemande systématique du "verbatim" et recoupement de la cohérence syntaxique PHP/Laravel, mais ce n'est pas un diff binaire du fichier ; à considérer comme une lecture de code fiable mais pas un dump certifié.

## Partie 1 — Fact-checking des affirmations du journal

| # | Affirmation du journal | Verdict | Preuve |
|---|---|---|---|
| 1 | Isolation totale des Organizations (drivers/users non partagés, doublons sans lien natif) | **CONFIRMÉ** | Architecture confirmée par le mécanisme `CompanyScope` (global scope Eloquent) trouvé dans `core-api/src/Traits/HasApiControllerBehavior.php` — toute requête est filtrée par `company_uuid`/session sauf `withoutGlobalScopes()` explicite. Aucune relation cross-company dans les modèles `Driver`/`User`. |
| 2 | `Fleet.drivers()`/`vehicles()` = relations **many-to-many** via pivot, driver dans plusieurs Fleets nativement | **NUANCÉ** | Faux au sens strict Eloquent : `fleetops-api/src/Models/Fleet.php` déclare `hasManyThrough(Driver::class, FleetDriver::class, ...)`, pas `belongsToMany`. Mais la conclusion pratique tient : la table pivot `fleet_drivers` (migration `2023_04_27_053456_create_fleet_drivers_table.php`) n'a **aucune contrainte unique** sur `driver_uuid` ni sur `(fleet_uuid, driver_uuid)` — rien n'empêche plusieurs lignes pour un même driver dans des fleets différentes. Un driver peut donc bien appartenir à plusieurs Fleets, "zéro duplication, zéro désync" reste vrai au niveau data, mais `hasManyThrough` n'expose pas nativement `attach()/detach()/sync()` (à gérer via des créations directes de `FleetDriver`, pas via les helpers Eloquent standards many-to-many). |
| 3 | `parent_fleet_uuid` — Fleets hiérarchisables | **CONFIRMÉ** | `Fleet::parentFleet()` (belongsTo self), colonne ajoutée par `2023_09_27_023757_add_column_to_fleets_table.php`. Corroboré par la doc officielle : "Fleetbase supports a fleet hierarchy where you can create a fleet and then sub-fleets under it." |
| 4 | `Vendor.connect_company_uuid` non exploité côté API | **CONFIRMÉ** | `VendorController.php` (`getAsFacilitator`, `getAsCustomer`, `export`, `bulkDelete`, `statuses`) n'y fait jamais référence. Nuance utile : la relation `connectCompany()` (`belongsTo(Company::class)`) est structurellement câblée sur `connect_company_uuid` par convention Laravel — elle fonctionnerait si exposée, elle est juste inutilisée dans la surface API actuelle. |
| 5 | `facilitator` polymorphique sur `Order`, types Vendor/IntegratedVendor/Contact | **CONFIRMÉ** | `Order.php` : `facilitator_uuid`+`facilitator_type` (cast `PolymorphicType`), `morphTo()`, accesseurs comparant à `Fleetbase\FleetOps\Models\{Vendor,IntegratedVendor,Contact}`. Corroboré par la capture réseau du journal (`facilitator_type: "fleet-ops:vendor"`). |
| 6 | Absence de Policy/gates dans `OrderController`, pas d'isolation sous le niveau Organization | **CONFIRMÉ pour le point précis, NUANCÉ pour la portée** | `OrderController.php` et son parent : aucun `authorize()`/`can()`/Policy invoqué pour les lectures. Mais il existe bien un système `Policy`/`Role`/`Permission` (`core-api` `Models/Policy.php`, basé sur `spatie/laravel-permission`) — système **par type de ressource**, pas de scoping ligne-à-ligne par facilitateur. Découverte notable : un correctif de sécurité documenté (**GHSA-3wj9-hh56-7fw7**, cité en commentaire dans `HasApiControllerBehavior::deleteRecord()`) a dû ajouter un filtrage `company_uuid` "defence-in-depth" pour empêcher une suppression cross-tenant — preuve qu'il y a eu, au moins une fois, une vraie faille d'isolation même au niveau Organization. Le test manuel de l'équipe reste la preuve la plus solide et est cohérent avec tout ce qui précède. |
| 7 | `api_credentials` scopée par `company_uuid` | **CONFIRMÉ exactement** | Migration `2023_04_25_094311_create_api_credentials_table.php` : colonnes `user_uuid`, `company_uuid`, `key`, `secret`, `test_mode`, `expires_at`. |
| 8 | Navigator : une seule clé API par build | **CONFIRMÉ exactement** | README + `.env.example` de `navigator-app` : `FLEETBASE_KEY` fixé au build, aucune UI de switch d'Organization mentionnée. |
| 9 | Bug MySQL `fleetbase` vs `fleetbase_sandbox` | **NUANCÉ** | `docker-install.sh` et `docker-compose.yml` du repo `fleetbase/fleetbase` utilisent tous deux systématiquement `"fleetbase"` (jamais `"fleetbase_sandbox"`, jamais le mot "sandbox") — confirme que le script d'installation n'est pas la source de l'incohérence. La cause exacte reste non localisable dans le code source public (probablement bakée dans l'image `fleetbase/fleetbase-api:latest`, hors dépôts). Piste complémentaire : Fleetbase documente officiellement un vrai environnement "Sandbox" isolé pour les tests d'intégration (cohérent avec la colonne `test_mode` d'`api_credentials`) — plausible que l'image tente de provisionner une base sandbox distincte que `docker-install.sh` ne crée pas. Hypothèse plausible, non prouvée formellement. |
| 10 | Dépendance à OSRM | **CONFIRMÉ, et précisé** | `OSRM_HOST` présent dans `docker-install.sh` ET dans `docker-compose.override.yml.example`. Point important : la valeur par défaut dans les deux fichiers est **`https://router.project-osrm.org`**, le serveur de démo public du projet OSRM — explicitement documenté comme non destiné à un usage production. À remplacer par une instance self-hosted avant toute mise en prod. |

## Partie 2 — Découvertes nouvelles (zones non explorées par l'équipe)

**`order_config` — réel, mais deux mécanismes coexistent dans l'écosystème.** Dans `fleetops-api` (branche `main`, v1.2.0, celle que l'équipe déploierait aujourd'hui), il n'y a **pas** de colonne `order_config_uuid` sur `Order` — le mécanisme passe par `Order.type` (string) + un modèle `Extension` avec `meta_type='order_config'` (`fleetops-api/src/Support/Flow.php` : `getOrderConfig()`, `getOrderFlow()`, flow JSON avec étapes, conditions `if`, exigences POD par étape). Un vrai moteur de workflow configurable par commande, mais peu documenté. En revanche, le paquet `fleetbase/customer-portal` (plus récent) importe et utilise `Fleetbase\FleetOps\Models\OrderConfig` avec une vraie colonne `order_config_uuid` — un modèle dédié qui n'existe pas dans le `fleetops-api` public actuel. **Décalage de version réel dans l'écosystème** : à vérifier précisément contre les tags/releases exacts avant de s'appuyer dessus. Dans les deux cas, Fleetbase offre nativement des types de commande/workflows personnalisables par Organization — à évaluer sérieusement avant de coder ça côté Echango.

> **⚠️ Contradiction directe avec le rapport 02 (architecture)**, qui affirme que `order_config_uuid` est une colonne réelle sur `Order` dans `fleetbase/fleetops` (repo qu'il désigne comme actif). Traité dans `docs/specs_echango_delivery.md` § Contradictions à vérifier — probablement lié à la même confusion `fleetops-api` (archivé) vs `fleetops` (actif) que celle relevée par le rapport sécurité, à trancher par une vérification directe en local.

**`service_area_uuid`/`zone_uuid` — vrai zonage géographique natif.** `ServiceArea` (polygone `MultiPolygon`, type par défaut `"country"`, hiérarchique) contient plusieurs `Zone` (polygone simple), avec méthodes `inZone()`/`pointsInZone()`. Un `Fleet` peut être rattaché à une zone géographique précise. Non exploité par le dispatch (cf. rapport 04), mais potentiellement utile pour restreindre l'aire opérationnelle d'une sous-organisation ou pour une tarification par zone (`ServiceRate`).

**Ledger — extension de facturation complète, pas juste consultée en façade.** `fleetbase/ledger` (packages `fleetbase/ledger-api` + `@fleetbase/ledger-engine`) implémente une vraie comptabilité en partie double, facturation (templates, cycle de vie, PDF), passerelles de paiement (Stripe, QPay, Cash), wallets, rapports financiers. Directement intégrée dans `customer-portal` pour générer des factures depuis les commandes. Pertinent pour les besoins de facturation futurs d'Echango — pourrait éviter de construire un système de facturation séparé (voir toutefois le rapport 03 sur l'absence de moteur de commission).

**Pattern multi-tenant officiel — existe et contredit en apparence le choix de l'équipe, mais à raison.** La doc officielle (`fleetbase.io/docs/platform/identity-and-access/organizations`) recommande explicitement le multi-Organization pour "internal departments", "white-label platforms" et "client isolation" — exactement le schéma que l'équipe a testé et écarté (§3.1 du journal) à cause du non-partage des drivers. Le choix de l'équipe (Organization unique + Fleet/Vendor) reste le bon pour l'effet réseau visé ; la doc officielle ne mentionne pas explicitement cette limite de partage de drivers entre Organizations, donc le test manuel de l'équipe a bien apporté une information que la doc n'aurait pas donnée.

## Partie 3 — Découverte majeure : `fleetbase/customer-portal`

C'est la trouvaille la plus significative de cette revue, vérifiée directement dans le code (pas seulement le README) : **`fleetbase/customer-portal`** est une extension **officielle first-party** (AGPL-3.0-or-later, PHP ^8.0, Ember 5.4, activement développée) qui fait déjà l'essentiel de ce que l'équipe prévoit de construire from scratch pour le persona "commerçant" :

- Authentification dédiée (`AuthController` : un `User` avec `type='customer'`, distinct des comptes console, tokens Sanctum séparés).
- **Scoping par compte réellement implémenté en code**, pas juste en théorie : `PortalOrderService::queryForAccount()` filtre les commandes par `customer_uuid`+`customer_type` correspondant au compte résolu (`->withoutGlobalScopes()` + `where` explicite) — exactement la couche BFF que l'équipe prévoyait de construire elle-même.
- `PortalAccountResolver::resolve()` résout le compte vers un **`Vendor`** (via une table pivot `vendorPersonnel`) ou un **`Contact`** simple — c'est littéralement le même modèle `Vendor` que l'équipe a identifié pour la "sous-organisation".
- Carnet d'adresses scopé par compte (`owner_uuid`/`owner_type`) — implémente nativement l'idée de pré-remplissage "adresse magasin habituel".
- Facturation via Ledger, tickets de support, quotes, paiement Stripe, `migrateCustomerOwnership()` pour convertir un Contact en Vendor en réassignant l'historique.

**Insight de synthèse pour l'architecture Echango** : `Order` a deux champs polymorphiques indépendants, `customer` et `facilitator`. Le persona "commerçant" correspond naturellement au rôle **customer** (celui qui commande/paie la livraison) — exactement ce que couvre `customer-portal`. Le persona "gestionnaire de petite flotte" (dispatch) correspond au rôle **facilitator** déjà testé par l'équipe. Un même `Vendor` peut être customer sur certaines commandes et facilitator sur d'autres — les deux personas s'emboîtent proprement sur les deux champs natifs de Fleetbase.

**Limites à vérifier avant de s'appuyer dessus** : (1) décalage de version potentiel avec `fleetops-api` (voir `order_config` ci-dessus) — à tester en réel ; (2) le frontend est un moteur Ember, explicitement écarté par l'équipe — mais rien n'empêche de consommer uniquement le **backend Laravel** (`fleetbase/customer-portal-api`) comme BFF tout fait, en gardant Flutter côté frontend ; (3) rien dans le README/le code consulté n'indique une vue "dispatch" pour le persona gestionnaire de flotte — `customer-portal` couvre le persona commerçant, pas le persona petite flotte.

**Recommandation** : avant d'investir dans le développement d'une interface + BFF custom complets pour le persona commerçant, tester l'installation de `fleetbase/customer-portal` en local (même procédure que FleetOps : `composer require fleetbase/customer-portal-api` + `flb-package-linker`) et évaluer soit (a) le rebrand de l'Ember engine, soit (b) l'utilisation de son API Laravel seule comme BFF, avant de réécrire cette logique de scoping/carnet d'adresses/facturation à la main.
